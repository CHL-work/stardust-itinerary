# Feedback and daily issue-only review

The feedback worker (`pnpm feedback:run`) is a bounded backend job started by the deployment's scheduler (for example cron or a Kubernetes CronJob). Database due-work and idempotency gates decide what each run does, and the worker has issue-only authority. Configure the GitHub publisher token only in the worker's environment; the web app and the disruption monitor do not need it. See [configuration](#configuration-verification-and-rollback).

The layout controls reuse existing allowlisted diagnostic action codes only: bottom-bar items and day chips record `navigate`, and the phone AI pill records `dialog_open`. No action code, page value or diagnostics field is added for the layout. The privacy-safe instrumentation test also scans the layout component files. The launcher is absolute at the page's top-right and scrolls away, with the headers keeping the reserved right padding. The Itinerary day-chip strip stays pinned while that page scrolls, but it is page-scoped content, not a global toolbar. The launcher has already scrolled away before the strip pins, is never covered and stays non-sticky. The layout styles the report dialog (a bottom sheet on phones) and the Advanced settings and feedback-operations disclosures with theme tokens; the launcher itself is not moved or restyled. See [screen layout](UI_LAYOUTS.md).

Technical controls are consolidated in **Settings → Advanced settings**, closed by default. The Permissions and usage pages are not primary pages; they remain owner-only. Activity is reached from the same Advanced area; profile, trip switching, owner Trip settings (including both trip dates), members, language, Calendar connection and sign-out remain ordinary settings. Native disclosures support keyboard and touch navigation.

## Reporting a problem

The feedback button sits at the page's top-right across the application, including authentication and legal pages. It scrolls away with the document; it is not a fixed/sticky floating control. The 44px touch target, safe-area insets and native modal dialog behavior are retained. Sending requires a currently authenticated, active trip membership. The dialog offers a short title, bug/suggestion type, description, optional recent-action attachment, a publication-policy notice and a saved receipt. There is no publication toggle: new reports are always eligible for redacted review and worthwhile sanitized issues. It works in every UI language. A failed or unconfirmed send keeps the exact draft in memory; retry reuses its submission ID. Reloading/closing the browser is not durable draft storage.

The optional diagnostic trail contains at most 50 allowlisted page/action/time entries from the preceding **10 minutes**, plus coarse browser/OS/form-factor, selected locale and online/offline state. Both browser capture and server persistence enforce the same window (with the existing one-minute forward-clock tolerance). It is held only in memory until the user submits, and can be previewed or excluded. It does **not** collect keystrokes, form values, DOM text, chat contents, screenshots, full URLs, identifiers, event/expense names, raw JavaScript errors or stacks. Marked buttons/forms/selects supply static semantic action codes; text input/change events are not recorded. Browser errors record a generic code only. This is not session replay or continuous telemetry.

Trip/member changes and sign-out clear the trail and draft. The dialog rechecks current server context and sends a server-generated HMAC scope proof bound to trip, member and app user. A stale tab/account rebind cannot submit an old draft as a different user. The API derives the actor from the authenticated session, locks current membership, validates the same allowlists, limits body size and enforces five new reports per rolling hour / twenty per UTC day across a user's trips. Exact payload retries precede rate limits; changed-payload reuse conflicts. All responses are private/no-store.

## Storage and visibility

Migration `0044_feedback_triage.sql` adds private reports, daily review runs/items, immutable issue payloads and append-only lifecycle records. It changes no itinerary, expense or preference tables. A reporter can read their latest twenty report receipts in the current bound trip. The platform operator (a verified Google identity listed in `OWNER_GOOGLE_EMAIL`) can inspect private reports and aggregate queue/run status under Advanced settings. Being a trip owner alone does not grant this authority.

Raw descriptions are user-supplied private text. They are not safe to copy into Git, test fixtures, analytics or logs. Removed members' reports/receipts, and reports from deleted trips, remain in the database for debugging (queued reports from a deleted trip are still reviewed and may still become a sanitized issue); active-identity checks prevent access through a tombstone or rebound member slot. Database backups include this data and follow the deployment's backup privacy and retention policy. There is no automatic report expiry.

**Every new report is eligible** for automated redacted provider review and a worthwhile sanitized GitHub issue. A neutral localized note behind the form's "?" button explains this before submission (D-088); the reporter cannot switch eligibility off. Eligibility does not guarantee review or publication when a report is unsafe, not actionable, duplicated or the worker is unconfigured. Do not put passwords, reservation codes or private travel details in report prose. Redaction is defense-in-depth, not a promise that arbitrary user prose can always be perfectly anonymized. Issues are created only in the operator's private repository (`STARDUST_FEEDBACK_REPOSITORY`), never the public source repository.

Previously submitted opt-outs remain private and are never retroactively enrolled. The boolean payload/receipt field and immutable database eligibility guards remain for compatibility. After current authorization/scope checks, exact historical retries return the original receipt before policy checks or quotas, using the original unfiltered payload hash. A changed payload with the same ID still conflicts. An old page attempting a **new** opted-out report receives HTTP 428 `FEEDBACK_POLICY_CHANGED` and no insert; it is never silently converted to eligible. Existing old-page failure handling preserves the draft; copy it before refreshing to the current disclosure. No migration or historical diagnostic rewrite is needed.

## Daily review and delivery boundaries

The backend, not a browser page, runs the worker. Its database gate allows at most one review attempt per UTC day, including retries; a claimed attempt can finish without a provider call when every report is rejected locally as unsafe. A new batch contains up to twenty eligible, unclaimed reports and continues excluding historical opt-outs. Failed or expired unfinished batches take priority and reuse the same report set on later available days, at most three attempts in total. An exhausted third attempt remains failed with its audit history; it is not silently recycled into a new batch. With neither an eligible new batch nor a retryable unfinished batch, no model call occurs. Any scheduled run can pick up due work; if the worker does not run on a given day, review waits for a later run. This is bounded daily processing, not an availability guarantee or unbounded replay of all historical feedback.

The reviewer uses exactly `gpt-6-astra` with medium effort through the official Codex SDK, with a 180-second attempt timeout. It is configured for a fresh empty read-only working directory, disabled shell/search/apps/plugins and disabled discovered MCP connections; unsupported connection configuration fails closed. Configuration and mocked tests do not by themselves prove a successful tool-free live run. It receives redacted report excerpts and coarse action sequences, not raw database access, trip data, other users' AI histories or GitHub credentials. Structured validation separates reported evidence from hypotheses and missing information. Issues explicitly state that the bug has **not** been independently reproduced. Non-actionable/unsafe reports are ignored and known duplicates link to an existing delivery record. Validated successful completions store returned token counts in feedback runs/events, separate from member planning quotas and planning usage records. Failed or unreported usage is not a reliable zero-cost measurement; this workflow does not estimate a monetary charge.

The model cannot create issues directly. A deterministic publisher targets the repository named by `STARDUST_FEEDBACK_REPOSITORY` with an independently configured Issues-only credential. Before the first delivery of each run it asks GitHub for that repository's metadata and refuses to publish unless GitHub reports it private, not archived and taking issues; the run then reports `publishing: refused` and every issue stays queued. It may only read that metadata, create an issue, or list issues in that repository to reconcile delivery; no comments, edits, labels, code, branches, PRs, merge, shell or deployment. Both provider input and issue output are sanitized and bounded. The publisher credential is explicitly removed from provider subprocess environments, including existing planning/research adapters; provider authentication remains separate.

Before the sole automatic POST attempt, the database durably records an immutable payload hash and opaque delivery marker. A known success records its exact issue URL/number. Network uncertainty or a crash after GitHub accepts the issue triggers read-only reconciliation, never a blind second POST. Each reconciliation reads at most three pages of one hundred issues from the verified repository, with a one-hour retry backoff and at most twelve reconciliation attempts. Each worker pass handles at most five delivery claims. A failure before dispatch after its reservation may miss a delivery; operator review is preferable to duplicate issues. Failed credentials/rate limits or exhausted reconciliation remain visible as blocked/uncertain deliveries. A marker outside the bounded listing window can remain unresolved even if GitHub created the issue. No automated coding agent is implemented or started.

## Configuration, verification and rollback

The application continues accepting reports when Astra, GitHub or scheduling is unavailable. A missing token means queued issues, not successful delivery.

`STARDUST_FEEDBACK_TRIAGE_ENABLED=true` enables review. Publishing separately requires `STARDUST_FEEDBACK_REPOSITORY` (`owner/name` of a private repository) and `STARDUST_FEEDBACK_GITHUB_TOKEN`, a dedicated fine-grained token restricted to that repository with **Issues: read and write** (and the implied **Metadata: read**), set only in the worker's environment. On GKE both live in the `stardust-feedback-env` secret, which only the `stardust-feedback-publish` job's own service account can read. That job sets `STARDUST_FEEDBACK_TRIAGE_ENABLED=false` and runs no model; the `stardust-feedback` job runs the reviewer without the token. Reconciliation searches the currently configured repository, so finish or block any uncertain delivery before changing `STARDUST_FEEDBACK_REPOSITORY`. Never place it in chat, browser, Git, command arguments or logs. A developer tool's GitHub connector (for example in the Codex desktop app) is not a runtime credential and must not be harvested or reused. Optional `STARDUST_BUILD_VERSION` accepts only a short/full hexadecimal Git commit ID for report diagnostics.

The reviewer flag defaults off in code. Publishing is separate: a configured token permits delivery of already queued issues even when the reviewer flag is off. Conversely, review can queue issues without any publishing token. To stop automatic feedback work, disable the worker's schedule, not just the reviewer flag. Configuration status reports capabilities independently and does not prove provider authentication or GitHub permissions. It reads the web process's environment, so it shows publishing as unconfigured when the token is set only for the worker.

The deployment's scheduler runs `pnpm feedback:run` periodically (for example hourly); the database determines due work. The worker reads `DATABASE_DIRECT_URL` (or `DATABASE_URL`) and takes no arguments. A manual run can consume provider quota and publish queued issues, so it is not a read-only status check.

Tests use synthetic reports and mocked provider/GitHub transports. They exercise authorization, HMAC rebind fences, caps/idempotency, bounded diagnostics, database immutability, duplicate resolution, malformed/adversarial output, UTC concurrency/retry gates, uncertain POST recovery and source-only frontend privacy checks. Do not publish fake issues or replay real traveler reports merely to test this system.

Migration 0044 is additive. On code rollback, preserve reports, immutable receipts and outbox evidence; disable feedback scheduling before any reviewed rollback to incompatible code. Backup, restore and migration rules are in [database](DATABASE.md); deployment is covered in [deployment](DEPLOYMENT.md) and [self-hosting](SELF_HOSTING.md).

## Official references

- [Codex SDK](https://developers.openai.com/codex/sdk/) — documented runtime/authentication integration.
- [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra) — exact requested model family.
- [GitHub Issues REST API](https://docs.github.com/en/rest/issues/issues#create-an-issue) — issue creation and token permissions. GitHub does not provide an application-level exactly-once guarantee; the durable marker/reconciliation boundary is ours.

Provider capabilities and policies may change. Public signup, throughput increases, broader repository permissions or automated fixes are out of scope and need separate review.
