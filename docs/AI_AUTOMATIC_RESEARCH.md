# Automatic public-fact research

The planner can request current public information without the user typing “search”. A shared prompt separates the research phase from the final answer and requests missing public evidence before the answer is finished.

There are no dedicated preference conversations or preference extraction. Manually saved [personal AI instructions](AI_CUSTOM_INSTRUCTIONS.md) enter only the full planner's user context, disabling its direct hosted tools when nonempty. Isolated research still receives validated public subjects, not the raw instruction block; public interests can inform recommendation topics. Instructions participate in sensitive-context/identifier/booking-secret checks. No background worker or public-only helper loads the private settings text.

The optional [Calendar import place helper](CALENDAR_IMPORT.md#missing-place-optional-ai-lookup) is a separate explicit-entry workflow, not an automatic planner research round. It reuses public-subject/query/source validation and the same isolated SDK tool boundaries with its own small structured address schema, 60-second deadline and explicit human apply step. It never receives the full Calendar title, description, attendees or history.

A dedicated `price` kind carries source-linked structured service/duration tariffs in `fact.priceQuotes`. The same public identity/query/source gates apply; private-context price lookups stay blocked. Quotes retain units, tax and fee uncertainty instead of becoming confirmed ledger charges. One venue lookup groups its published tiers; only `venue` can also request structured hours. See [booking-price contract](AI_BOOKING_PRICES.md).

Broad public discovery is separate from exact venue-hours extraction. Multi-phase requests keep a bounded final-answer reserve, and finalization failures are reported by their actual cause. There is no extra search round, model change or replay of prior requests. Execution limits and recovery behavior are described below.

The initial venue lookup also collects optional structured opening hours, and exact validated evidence is reused after final planning. Returned results and original failure reasons are preserved independently of workspace/SDK cleanup. See [hours identity, privacy and notices](AI_VENUE_HOURS.md).

Typed Claude failure categories are kept for safe phase auditing, while this optional phase keeps its unverified fallback. A provider failure is not evidence that a public fact was verified. There is no additional lookup, automatic model switch or retry; see [provider failures](AI_PROVIDER_FAILURES.md).

## Request flow

1. The selected model reads the normal authorized context. Explicit public discovery retains its existing hosted-search path; ordinary planning does not gain a search tool over private context.
2. When public facts are needed, the model returns up to three `researchRequests`, each with `kind`, a short public `subject`, and an optional date. Kinds are `venue`, `discovery`, `travel`, `exchange_rate` and `price`. The initial reply should be a minimal request/acknowledgement, not a speculative full plan or candidate patches. Intermediate proposals/messages are not persisted as completed results or applied.
3. The server validates and projects eligible subjects into ephemeral `R1`–`R3` targets, plus exact hours targets for eligible dated venues using the trip time zone. A fresh isolated same-model researcher receives only these public targets, current UTC time and controlled lookup instructions. It has hosted search and a result serializer, no app database, full prompt, history, receipt, images, member directory, shell/files or general-network tools. Strict wire schemas require both `facts`/`hours` arrays; legacy facts-only results remain parseable.
4. Observed search, exact target identity and usable HTTPS sources are required for a source-backed fact. Wrong/missing/duplicated targets, unsupported sources and provider failures yield unverified outcomes. The final no-tools planner receives that actual evidence/outcome and the original authorized request, returns a final answer and validated proposals, and may not initiate another research round.
5. Existing timestamp repair, financial/privacy checks, optional venue-hours advisories, final membership/revision fences, owner approval and atomic saved-result recovery remain in force. Intermediate requests never become extra user messages or quota units.

The model is instructed to research uncertain, niche or changeable public facts such as ticket rules, opening times, venue details, service/duration tariffs, transport information, such as a flight's terminals for its date (JOB-082), and exchange rates. Supplied booking facts, payer/split choices and arithmetic do not need research. Explicit no-search wins. This is model-directed bounded retrieval, not a guarantee of exhaustive search or independently verified pages.

`discovery` covers public city/area, franchise, otaku-shop, exhibition, collaboration and pop-up topics before an exact venue is known. Controlled queries ask for official events, locations and dates, not detailed opening intervals. Short summaries must identify actual venue/branch and applicable published dates, prefer official organizer/venue/franchise sources and exclude expired or wrong-location matches. A supplied date must match; `date=null` means current or explicitly dated upcoming findings, not an undated availability claim. No supported match is not proof that nothing exists. Discovery-only answers use a concise sourced shortlist and `proposals=[]`; lookup alone grants no mutation authority. Partial evidence should produce the supported portion plus specific uncertainty, not another research request or an unsolicited full itinerary. The kind is explicit model output, not a heuristic city/franchise-name classifier.

For an already specified public meal/activity venue/date, the planner requests the dated venue lookup early when permitted, combining needed hours/ticket/venue facts. Authorized dated `venue` subjects gain exact name/date/trip-time-zone `hoursTargets`; no preliminary proposal or extra private context enters research. Optional structured hours are validated separately from prose using observed per-target search, exact identity and sourced period rules. Complete matching attempts, including explicit unknown, are not repeated after final planning. Changed identities or legacy/missing/invalid hours may use the budget-gated fallback. Latest currency queries remain dated direct-pair reference information; no payment data is added.

## Privacy and money

Subjects reject identifiers, URLs, control characters, instruction-like text, member names and known private event labels. Explicit private context, booking-secret/identifier or sensitive-memory gates block venue/discovery/travel/price research. The narrow exception is a **latest public currency pair**, such as `HKD/JPY`, with `date=null`: only supported currency codes are sent, never an amount, receipt date, payer, split or traveler. Explicit no-search also blocks this exception. Private event research is not enabled by this feature.

An exchange-rate fact is dated, indicative reference information, not the actual bank/card rate, a future rate or a ledger instruction. The original supplied currency and final paid/owed amount are retained by default. There is no deterministic FX conversion engine, automatic ledger revaluation or separate expense schema for research. The model must not substitute JPY for an HKD receipt merely because the trip currency is JPY.

Research summaries and source pages are untrusted data, not instructions. Facts cannot change identities, permissions, amounts, dates, privacy or owner-approval rules. Only public sanitized sources are returned. The provider does not receive private context; Codex query inspection is post-execution evidence rather than a pre-execution firewall. Claude additionally validates query input in its pre-execution hook. Source-backed model extraction still can be inaccurate; source dates and uncertainty matter.

## Budget, failure and durable results

The overall work budget is **180 seconds for text / 225 seconds for images**. The single optional lookup round has a **90-second cap**; its launch budget subtracts a **60-second final-planning reserve** from remaining time and still needs at least eight seconds to start. The reserve is budget allocation, not a guarantee that a provider finishes in 60 seconds; all phases share the remaining overall deadline. Initial browser waits are 200/245 seconds, the route ceiling is 300 seconds, and the ten-minute in-flight fence still applies. Instructions limit retrieval to a distinct initial query per target, one indispensable follow-up across the run and one best source-page inspection per target; these prompt limits are backed by the hard deadline, not an exact tool-count firewall. Empty Codex source-page actions do not count as queries or independently verify another target. A bounded race aborts overdue research. No automatic retry or stronger-model fallback is added. Reused hours need no extra call; remaining optional hours work still needs at least 30 seconds left and is capped at 60 seconds.

If research fails, is blocked or lacks evidence, final planning explains the specific missing facts and can still preserve a concrete supplied-data proposal. If final planning cannot complete, neutral selected-language feedback distinguishes insufficient remaining time, final-answer timeout, unsupported additional research, provider failure or other finalization failure. Known provider failures use the existing safe provider/reset and role-appropriate manual guidance. A final-answer failure is not relabeled as failed verification or evidence that a venue is closed. The saved fallback contains no proposals or new preference candidates; the unfinished answer/patch is never substituted. Failed unreported provider usage makes the total unknown while known phase receipts remain. One admitted prompt counts once.

Cleanup is independent for both research and main planning. Successful returned research evidence/usage survives SDK/workspace disposal errors. A completed main-planner answer continues through normal validation, authorization and completion fences even if bounded temporary-workspace cleanup fails; this never grants direct-write authority or makes an invalid answer successful. Claude planning closes its query on completion/abort. Cleanup failures retain safe independent audit metadata without paths/raw diagnostics, and an original timeout/provider failure remains primary. Failed cleanup may leave local temporary state; it does not permit broad deletion, retries or a deadline extension.

`public.research.requested`, `public.research.completed` and `public.research.finalized` record bounded counts, outcomes, safe public search/source evidence and reported usage, not extra private prompt copies. They also carry hours-target/valid-evidence/completed-attempt counts and independent cleanup metadata. Finalization also records the original `researchOutcome`, `finalizationBudgetMs` and, when applicable, a safe `failureReason` and allowlisted `providerFailure`; this separates lookup outcome from answer completion. Main-workspace cleanup retains its independent `workspace.cleanup.failed` receipt. `provider.attempt.completed` distinguishes final planning. Only the final answer and proposals enter the existing success/history/recovery transaction. Exact-key replay and mobile recovery return that saved result without searching again.

The prompt prohibits blanket “no search this turn” and “hours were not checked” statements. It describes topic-specific evidence instead; final deterministic notices report reused or fallback evidence honestly. The narrow official THEキャラ article URL exception preserves exact public citations without widening generic query-string permissions. This does not retroactively rewrite stored old replies or existing events.

## Verification and operation

The opt-in full-flow discovery evaluator is `scripts/test-ai-research-completion.ts`. Read its current allowed model/date arguments before a live run; it calls the configured provider and consumes its quota. The caller must create a fresh empty loopback `stardust_test_ai_completion_*` database distinct from the app database and set `TEST_DATABASE_URL` plus `TEST_DATABASE_CONFIRM_DESTROY` to that exact name. It currently pins 45 migrations through 0049, not the current schema head; this is a scoped synthetic evaluator, not a full current-schema migration check. It uses fixed public topics/synthetic identity and requires multiple searches, a completed answer, zero proposals/canonical changes and unchanged exact-key replay. Honest unavailable findings are not a sourced benchmark pass; failed/timed-out research never passes. The caller removes only the exact disposable database and verifies absence. Never use real traveler chats/instructions as fixtures.

`pnpm check` covers shared prompt/schema, public projection and provider boundaries, final planning, no-evidence/failure/opt-out/privacy/budget cases, usage, draft continuation, replay and approval fences. The opt-in `scripts/test-ai-automatic-research.ts` requires a fresh empty loopback `stardust_test_ai_auto_*` database distinct from the app database and consumes provider quota. It also currently pins 45 migrations through 0049 and synthetic fixtures. It checks a public visit plus original HKD charge and reference-rate research, then exact saved-result replay, with no canonical fixture mutation. Do not point it at an application database. The caller must remove the exact disposable database and verify absence afterward.

The default live evaluator is a strict sourced-FX benchmark. A separate `--allow-unverified` workflow mode also accepts genuinely unverified FX after an observed pair lookup, an explicit uncertainty response and no invented quoted rate. It does not accept failed/timed-out research or unfinished finalization. Both modes check the exact pending original-currency expense, canonical-table snapshot and replay before classifying FX evidence. A verified venue cannot stand in for an unverified rate. This separates correct application behavior from the availability of a current published quote. English message checks are synthetic-evaluation sanity checks, not production prose enforcement or independent source proof.

Deploy and recover with [deployment](DEPLOYMENT.md) or [self-hosting](SELF_HOSTING.md); backup, restore and migration rules are in [database](DATABASE.md). A rollback must preserve all financial/privacy/recovery guards and additive history.
