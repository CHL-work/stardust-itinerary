# AI venue opening-hours checks

Hours are checked for an AI-proposed public meal/activity visit, even if the user only says to create the event rather than explicitly requesting search. Relevant canonical/pending venue, date, time, type and visibility edits, plus restores, are also checked. A title-only or note-only edit does not trigger research. Pending edits keep the same request and original linked expense. The feature does not silently move, delete, approve, reserve or book anything.

Eligible initial public venue research requests optional structured dated hours in the same lookup. Exact venue/date/time-zone evidence is reassessed against the final validated event times without a second search. An explicitly researched unknown is also a completed attempt, not a reason to repeat the lookup. Unverified results use short informational notes; only supported closure/time/cutoff conflicts use a warning. Existing saved replies are not rewritten.

[Automatic public-fact research](AI_AUTOMATIC_RESEARCH.md) may run before the final planning turn; its lookup carries structured hours without replacing deterministic assessment. The final planner receives actual researched or unverified outcomes and must not claim blanket "no search" or "hours not checked". Both phases share the original overall deadline; absent reusable evidence, insufficient time for a fallback stays explicitly unverified.

The `discovery` research kind covers broad city/franchise/pop-up subjects. Even a dated discovery target cannot become a structured hours target; only exact dated `venue` subjects qualify. Discovery facts do not prove opening intervals for a later chosen venue. `price` targets research published tariffs only; they do not become structured hours targets or establish that the venue will be open. See [booking prices](AI_BOOKING_PRICES.md). The request timing below does not relax identity, source, privacy or deterministic time checks.

Documented Claude terminal failures are classified for safe audit metadata. An unavailable optional hours check still produces the unverified outcome and does not discard valid proposals or imply confirmed opening hours; see [provider failures](AI_PROVIDER_FAILURES.md).

## Initial research and deterministic final assessment

1. Initial isolated public research receives at most three authorized subjects. Dated venue subjects additionally become exact public `V`-key/name/date/time-zone hours targets. Both SDK wire schemas require `facts` and `hours` arrays (`hours=[]` without eligible targets); the parser tolerates legacy omitted hours. Per-target observed search, exact binding and deterministic source/interval validation are required before reuse. Ordinary prose, a URL alone, omitted output and malformed rows never count as verified hours or a completed attempt. A valid explicit unknown has empty periods/sources and counts only as a researched unknown.
2. Final planning and optional timestamp repair produce a validated proposal batch. Reuse matches the complete venue/date/time-zone identity, never an ephemeral key alone or fuzzy branch similarity; final start/end times are compared again. The prompt preserves the researched location label for the same venue. Private or changed targets cannot borrow another result. Only remaining eligible targets may use the optional isolated hours researcher, at most four, with sufficient remaining budget. Legacy facts-only provider output remains valid and permits that fallback.

The additional prompt never receives the original request, chat history, checkpoint, preferences, member/DB identities, event titles/notes, pictures or financial/booking fields. Initial targets derive only from already-authorized public research subjects, not preliminary proposals. Final publicness requires explicit trip visibility in both existing and proposed state, so changing a private event to public does not automatically export its prior venue. Private, untimed, unsafe/identifier-bearing and member-name-bearing candidates are not researched. Existing sensitive-prompt/booking-secret and sensitive-memory gates, plus an explicit no-search instruction, skip research and return quiet explanatory notes. Hotel stays, transport routes, expenses and notes are not ordinary meal/activity opening-hour checks; imported hotel check-in/out facts are preserved.

Main-planner explicit search intent and its required-evidence failure rule still apply. Automatic hours lookup does not enable search on the full private planning context. Both Codex and Claude retain the selected authorized model/effort, provider-supported authentication and a fresh temporary read-only workspace. Only hosted search and the side-effect-free result serializer are allowed; commands, files, general network, MCP/app access and arbitrary tools are not added. Claude validates search inputs in a pre-execution hook as well as inspecting observed tool calls.

## Evidence and deterministic decisions

The researcher returns per-target identity/date/time-zone, `hours_found|closed|unknown`, up to six explicit-offset opening/closing periods, optional per-period last admission/order, and supporting public HTTPS sources. Instructions prefer current official or venue-confirmed information, account for weekly/holiday/special closures, split lunch/dinner service and overnight periods, and use unknown for ambiguous branches, conflicting or incomplete evidence.

The server requires observed search, exact target binding and at least one usable supporting URL. Unknown/duplicated keys, wrong dates/branches/time zones, impossible/overlapping intervals, missing evidence and unsupported sources produce `unverified`, not an inferred closure or fabricated open claim. Unsafe sources are omitted without discarding a different usable source. The strict public URL filter allows exact numeric Tabelog restaurant landing paths, never arbitrary account/booking/confirmation paths. Query parameters are normally removed. The only retained article query is one positive 1–7-digit `p` on the official HTTPS `the-chara.com`/`www.the-chara.com` `/blog/` endpoint; known tracking/hash is removed and credentials, nonstandard ports, duplicate IDs or private/preview/unknown parameters are rejected. This retains an exact public source instead of replacing it with the blog homepage. The global disruption sanitizer is unchanged.

The deterministic result is one of:

- `closed`: published evidence reports no opening period for the planned date.
- `outside_hours`: arrival is outside all published sessions, or the visit extends past closing.
- `last_admission`: arrival is at/after a published last-order or entry cutoff.
- `published_hours`: the planned interval fits published hours, with an explicit same-day/queue/seats/reservation caveat.
- `unverified`: no sufficient eligible, valid evidence was obtained.

Notices are prepended to the selected-language AI reply and saved proposal reason, so own-chat history and exact-key result recovery retain them. `closed`, `outside_hours` and `last_admission` use ⚠; `published_hours` and `unverified` use ℹ. Unknown notes distinguish opt-out, privacy, missing place/time, exhausted budget, target cap, timeout, provider failure, missing observed search and insufficient evidence, without exposing private or upstream diagnostic text. Both Cantonese modes use neutral wording. Valid proposals and approval/financial/privacy rules remain intact. These are planning-time advisories, not a new event-card icon, background monitor, phone notification or retroactive rewrite.

This is source-grounded model extraction followed by deterministic time comparisons, **not independent verification of every page or a guarantee that a venue is open**. Codex exposes search queries but not a complete independently inspectable source-result list; source URLs remain model-reported evidence. Claude also exposes some search result URLs. Regular schedules may miss special closures, queues or sold-out service. Confirm important visits with the venue. The trip time zone must correspond to the venue; uncertain cross-time-zone branches should remain unknown.

## Budget, logging and failure behavior

Initial hours share the single public-research round's **90-second cap**, with **60 seconds reserved from remaining time for final planning**. A remaining post-validation lookup still starts only with at least **30 seconds** left and is capped at **60 seconds**, inside the overall **180-second text / 225-second image** work budget. The reserve is not a provider-completion guarantee. No retry or automatic stronger-model fallback is added; additional candidates or insufficient time receive informational notes. Abort plus a bounded race prevents a stalled optional lookup from discarding or indefinitely delaying a valid proposal. Workspace and SDK disposal failures are separate `cleanupFailed` metadata: they never erase returned evidence/usage or overwrite the primary research/timeout/provider outcome. Main-planner workspace cleanup is independent as well, with all completed output still subject to normal validation and authorization. Bounded failed cleanup can leave an isolated temporary workspace; no broad cleanup deletion is authorized.

`public.research` receipts add hours-target/evidence/attempt counts. `venue.hours.reused` records source phase, count and proposal indexes; `venue.hours.checked` adds per-item evidence origin and a bounded unverified reason. Existing started/completed receipts retain model/count/budget, sanitized sources, usage and independent cleanup flags, not extra private prompt copies. Notices share the existing proposal and durable result transaction. Usage is added once to the admitted request; reuse/skips add no provider call or usage. A started failed lookup with unreported usage makes the aggregate unknown while prior receipts remain. User-bound concurrency, replay-before-quota, final membership/revision fences and owner audit access remain.

The public-only scripts are `scripts/test-ai-venue-hours.ts` and `scripts/test-ai-venue-hours-reuse.ts` (the latter requires `--run-live`). Read their current CLI contract and select an allowed model and an explicit appropriate `--date`. Fixture dates from earlier runs are not today's schedule.

This public-only Monday-closure fixture researches the named Akihabara restaurant without loading `.env.local`, using an app database, reading a real conversation or writing events/expenses. It consumes ordinary provider quota and cleans only its exact generated temporary directory. Select a real Monday explicitly and recheck the venue's published rules when reusing the fixture; it must not silently convert an unknown result into a pass. Console diagnostics are limited to public-fixture classifications, match booleans, source domains and usage.

The reuse evaluator makes one public-only THEキャラSHOP lookup with exact hours targets and reuses evidence for a synthetic visit, without a database or app conversation. It reports safe counts/classifications/source domains. Prose-only, unknown, unsearched or invalid evidence is not a successful sourced benchmark; cleanup failures are separate. Both scripts consume provider quota only when explicitly invoked.
