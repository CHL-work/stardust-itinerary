# AI request continuity on phones

Preference-mode execution is retired. Its historical chats are read-only and cannot become active through recovery or stale submissions. Historical response decoders accept then strip retired preference receipts/counts, preserving ordinary saved replies. New Settings instruction text is captured once per request; reconnect/replay returns the original saved answer without reloading instructions or invoking the provider. A later new request uses current saved instructions. See [personal AI instructions](AI_CUSTOM_INSTRUCTIONS.md).

The explicit Calendar venue lookup shares the bound-user admission lock with planning (`planning` and `calendar_location` cannot overlap for one user). It stores a separate non-conversation request and exposes self-only lookup GET recovery, not a planning-history turn. Exact retries do not restart the provider or charge again; completed evidence can issue a fresh actor-bound review receipt. See [Calendar import contract](CALENDAR_IMPORT.md). Planning conversation recovery and separate-user concurrency remain unchanged.

Work budgets are 180 seconds for text and 225 seconds for images, with initial browser waits of 200/245 seconds and a 300-second route ceiling. These are bounded execution/delivery limits, not a durable queue or a promise of provider availability. The ten-minute abandoned-request fence, same-user isolation, idempotency and provider-free mobile recovery still apply. A final answer that cannot complete after research is saved as reason-specific neutral feedback with no proposals, so returning to the phone recovers that outcome instead of silently replaying the request.

Optional allowlisted `providerFailure` metadata travels through direct delivery and self-only recovery. Read only the latest request.failed event for the exact authorized trip/request; its code must agree with the canonical failed request. Legacy/malformed metadata stays generic, never backfilled from a later provider probe. Recovery still only reads completed failure and never retries it. See [provider errors](AI_PROVIDER_FAILURES.md).

[Automatic public research](AI_AUTOMATIC_RESEARCH.md) also stays inside the original request and deadline: initial planning may request one isolated lookup, then one final no-tools planning turn consumes the actual evidence or failure outcome. Intermediate replies/proposals are not published or persisted as completed changes. Only final validated proposals and the final answer commit through the existing fenced transaction; if finalization cannot finish, a localized no-proposal answer is saved instead. Reopening or keyed replay recovers that answer without repeating research or consuming quota. This adds no provider session, queue, background retry or concurrency exception.

Exact validated venue/date/time-zone hours from the initial isolated lookup may be reused, including an explicit researched unknown that prevents a duplicate matching attempt. Unmatched eligible proposals may still use the bounded hours fallback after final planning/validation. Both share the original request/deadline and finalization fence. Localized neutral uncertainty notes, supported hours-conflict warnings and public sources are saved in the same reply and keyed response receipt; replay or recovery does not research again or consume another prompt. Optional cleanup errors do not erase successful evidence or relabel an original timeout/failure. A failed optional lookup preserves valid proposals with informational unverified-hours feedback, not a new failed conversation or automatic retry. Existing saved answers are not rewritten. See [venue-hours budgets](AI_VENUE_HOURS.md).

The `update_pending` action edits the existing approval request inside the same transaction as its success/recovery receipt. A replay returns that same request ID without another proposal revision, model call or quota charge. Failure to save completion rolls the edit back. See [pending edits](AI_PENDING_EVENT_EDITS.md).

Short admission/completion transactions are also serialized with trip-role/removal changes. No trip lock spans a model call; different users still execute provider work concurrently. A removed member's requests/conversations are interrupted and retained for history, not replayed or assigned to another identity. See [member removal](PUBLIC_TRIPS_AND_MEMBERS.md#removing-a-member-safely).

[Picture imports](AI_IMAGE_INPUTS.md) bind ordered normalized-image hashes to retry identity. Images allow 225 seconds total work and a 245-second initial browser wait; text-only work allows 180 seconds with a 200-second wait. The extraction sub-budget remains 45 seconds. Unsent/retry pictures are memory-only; submitted pictures become private database history.

## What the busy message means

A suspended phone page can lose a long POST response even though the server continues and logs success or failure. Request execution is therefore separate from **delivery recovery**: the result is saved server-side and recovered later, so the user does not need to resubmit a prompt that is still running. A private conversation still belongs to one bound user and trip. Admission serializes that bound user across trips, not the group: different users can execute concurrently, while one user can have only one recent planning request in flight. The busy message therefore refers to the signed-in user's own in-flight request, possibly in another trip, not to other travelers. Database locks are held only during short admission/completion transactions, never through a provider call. Resetting conversation memory cannot bypass active work.

## Durable identity and results

The browser assigns a random `clientRequestId` to an explicit submission. Migration `0033_ai_request_recovery.sql` adds nullable client identity, SHA-256 payload digest and safe response JSON to `ai_requests`. The key is unique per trip and bound user. Under the user admission lock, an exact repeat is looked up **before** quota/model policy and returns its previous delivery state; a changed prompt/model/locale with the same key is rejected. An admitted failed, expired, reset or interrupted key is never automatically executed again. Pre-admission policy/setup failures have no committed client key and retain their existing separate audits; no provider or proposals ran for that rolled-back attempt. Unkeyed/internal callers keep their compatibility behavior; this does not make an old-schema application version a safe writer.

The safe success response is stored inside the proposal/completion transaction. It includes the answer, proposal IDs/status, model, quota receipt, public-search sources and bounded memory-use counts—not raw prompts, provider diagnostics or hidden audit payloads. Database constraints require a member-owned successful completed request, JSON object shape and a 128 KiB bound; the reader additionally validates the exact response allowlist. Legacy rows can recover their saved answer without inventing missing metadata.

Final proposal writes are fenced against a still-active, unexpired request, active bound membership and the same open conversation. All proposal paths use the transaction-aware repository boundary, including non-create operations. An expired worker cannot commit late proposals after a replacement request is admitted. The ten-minute abandoned-request window is a lock/recovery safety bound, not permission to exceed the 180-second text/225-second image processing budget. Independent main-workspace cleanup failure does not discard returned output, but all normal validation and finalization fences still apply before any result is saved.

## Delivery and frontend behavior

A separate [private history view](AI_CONVERSATION_HISTORY.md) lists past conversations. Recovery still observes the active conversation; browsing an archive does not move it. Explicit continuation makes the selected user archive active, while identity-revoked history remains inaccessible. Web submission now binds `conversationId` into admission and the retry digest, including explicit `null` when no active conversation was observed. Recovery GET also supplies the current conversation ID so stale browser tabs can refresh without silently routing a new question elsewhere.

`GET /api/trips/:tripId/ai` returns only the signed-in user's latest recoverable request in the active conversation. An optional `clientRequestId` selects that user's exact submitted request. Status is `running`, `succeeded`, `failed` or `interrupted`. Current trip, membership, user binding and conversation-era checks prevent cross-user, cross-trip, reset-history or revoked-identity reads. Work in another trip exposes only a busy boolean through this endpoint, never that trip's answer. Responses are authenticated and `no-store`; GET never starts a provider or charges quota.

The bounded POST remains independent of the browser request's abort signal on the long-lived Node server. Client GETs have a 15-second transport timeout; POST delivery waits are 200 seconds for text and 245 seconds with images, above their work budgets. Aborting delivery does not resubmit or cancel server work. The client checks saved status on initial page load, visibility return, focus, online and browser restoration. Visible active/reconnecting pages poll every five seconds; idle pages every thirty seconds; hidden pages skip polling. Checks are deduplicated, and identity changes/unmounts invalidate late responses. A recovered terminal answer releases logical submission even if its old HTTP response remains pending; generation ownership stops that response clearing newer work. Authorization loss invalidates old responses before private text can reappear. Completion refreshes the itinerary/proposal projection once per request. AI work does not hold the app-wide UI busy flag.

No prompt or answer is written to browser storage for recovery; a full reload finds the latest request from PostgreSQL. A live page retains an uncertain submission key in memory for an explicit identical retry. Returning to the app never automatically re-POSTs a prompt. Localized processing, reconnecting, other-trip-busy, timeout and interruption messages explain the state; both Cantonese modes use neutral reliability language. Stored AI answers remain in their original generated language.

## Limits and verification

This is delivery recovery: provider work runs in the application process that admitted the request, not in a durable distributed worker queue, and there is no automatic provider retry. If the process dies, the previous key remains non-replayable and eventually reports interrupted; inspect pending changes before explicitly retrying. Switching apps cannot prevent provider timeouts, account limits, host downtime or expired sign-in. Model choice, member quota, approval, privacy and memory limits remain unchanged. Closed-app push is not implemented.

Regression tests cover separate-user concurrency, same-user admission/reset blocking, idempotent repeat/mismatch, expired completion fencing, response serialization, self-only recovery, binding/revocation/reset boundaries, mobile polling, missing/late responses, safe legacy answers, localized states and zero automatic submissions. Run `pnpm check` against an explicitly confirmed disposable database ([database tests](DATABASE.md#5-tests)). Deploy with [deployment](DEPLOYMENT.md) or [self-hosting](SELF_HOSTING.md).
